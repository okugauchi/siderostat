## 2. 検証シナリオ（配布仕様 12、13、14、16.3、16.4 節対応）

E-05 の Actions 5 件に対応する検証シナリオ。

### シナリオ 1: legacy job 稼働中から migration 成功（仕様 12.2 / 16.3）

- 前提: legacy LaunchAgent（`local.siderostat.runtime` / `local.siderostat.monitor`）と
  `/usr/local/bin/siderostat[-monitor]` が存在し、legacy job が稼働している。
- 手順: first launch / migration フローで legacy inventory を検出 → drain → stop →
  legacy plist を backup へ退避 → new runtime を `SMAppService` 登録 → readiness 確認。
- 受入: port（18080/18081/9920/18082/9911/8000）と DS4 child に重複がない。old/new
  runtime が同時に同じ port を listen しない。legacy binary は自動削除せず「削除可能」表示のみ。
- 現状: 両ノードとも legacy install が存在しないため、実機でこのシナリオを再現するには
  legacy 環境の復元が必要。現行の検証対象は build 11 を起点とする upgrade / rollback /
  uninstall であり、ユーザー判断により v0.2.1 の復元は行わない。本シナリオは現行 gate の
  対象外（N/A）とし、migration 契約は機能テストで確認済み。

### シナリオ 2: 失敗 migration の legacy rollback（仕様 12.2 rollback path）

- new registration または readiness を意図的に失敗させ、legacy plist を戻して以前の job を再開。
- 受入: rollback 後、legacy job が再開し、port / child 重複がない。user data は不変。
- 機能テストで `cutover_*_rolls_back` 系の全パスを検証済み。

現行環境には legacy job が存在せず、ユーザー判断により v0.2.1 の復元を行わないため、
本シナリオも現行 gate の対象外（N/A）とする。失敗時 rollback の状態機械・driver 契約は
機能テストで確認済みである。

### シナリオ 3: v0.3 candidate 間 upgrade で data 保持（仕様 13.1 / 16.3）

- prior/final candidate `.pkg` で `/Applications/Siderostat.app` を更新。
- 受入: config、secret、manifest、model、KV cache が保持される。active runtime が旧 image で
  動き得る場合、monitor が app/runtime version 不一致を通知し、ユーザーの明示操作で再起動できる。

### シナリオ 4: prior notarized package への rollback（仕様 13.2 / 16.3）

- prior notarized `.pkg` を保持し、config migration の backward compat / backup restore を確認。
- 受入: version mismatch の案内が出る。model、manifest、secret、KV cache を rollback で削除しない。

### シナリオ 5: uninstall（仕様 14 / 16.3）

- menu で background service 停止 → runtime unregister → monitor 終了 → app を Trash。
- 受入: service だけが止まり、Application Support、secret、model、cache は既定で残る。
  「すべてのデータを削除」は対象 path を列挙し再確認する専用操作。

## 4. 実機検証計画（change window 確保後に実施）

### 4.1 実施前に必要な操作（操作ガイド）

実機検証は本番稼働クラスタを一時停止・再構成するため、**ユーザーの change window 承認と
手作業が必要**。agent は sudo を除くコマンド実行・ログ収集を担当する。

1. **change window の確保**: クラスタを停止してよい時間帯をユーザーが指定する。
2. **legacy scope の確定**: 現行 build 11 の両ノードに legacy install がなく、ユーザー判断に
   より v0.2.1 は復元しない。シナリオ 1/2 は現行 E-05 gate の対象外（N/A）とし、
   migration / rollback 契約の機能テスト evidence を代替証跡とする。
3. **package の準備**: 実施済み。candidate `.pkg` を両機の `/tmp/` へ配置・integrity 確認済み。

#### 準備済み package（両機の `/tmp/`、checksum 一致確認済み）

| 機 | package | build | SHA-256 |
|---|---|---|---|
| 両機 | `/tmp/Siderostat-0.3.0.pkg` | 11（現行） | `c1e81920…38a0ea4` |
| 両機 | `/tmp/Siderostat-0.3.0-build10.pkg` | 10（prior、修正版） | `60d6fe96…62c563` |

build 10 の旧 package（`9424db34…43dfe6`）は payload が build 11 だったため使用しない。

Gatekeeper を確認済みである。

#### 検証ヘルパー `scripts/e05-verify.sh`

E-05 の実機検証時に状態採取・比較・検証を行う read-only helper。クラスタの停止・変更は
行わない（change window 中にユーザー/agent が明示的に操作する）。

```sh
./scripts/e05-verify.sh snapshot <label>    # 現在の状態（env/userdata/process/port/job/readiness）を保存
./scripts/e05-verify.sh compare <a> <b>     # label a/b の user data digest・mode を比較
./scripts/e05-verify.sh processes           # runtime / ds4 process 一覧
./scripts/e05-verify.sh ports               # 関連 port LISTEN 一覧
./scripts/e05-verify.sh jobs                # new/legacy runtime job 状態
./scripts/e05-verify.sh readiness           # /healthz /readyz
./scripts/e05-verify.sh all <label>         # 上記まとめて
```

- snapshot の `userdata.txt` は config / cluster-state / manifest の SHA-256 と secret の
  mode（本文は含まない）。`compare` で upgrade / rollback / migration 前後の data 保持を判定。
- baseline snapshot を採取済み（2026-08-22）: ローカル `/tmp/siderostat-e05/baseline-20260822`、
  Mac Studio `/tmp/siderostat-e05/baseline-20260822`（両機とも v0.3.0 / build 11、分散クラスタ active）。
- スクリプトはリポジトリ `scripts/e05-verify.sh` に配置（実行権限付き、`bash -n` で構文確認済み）。
  リモート実行時は `/tmp/e05-verify.sh` にコピーして使用。

### 4.2 実機検証手順（各シナリオの操作ガイド）

#### シナリオ 1（migration 成功）

cutover は仕様 12.2 の順序（drain → stop → legacy plist を `Application Support/migration-backup/`
へ退避 → new runtime を `SMAppService` 登録 → readiness 確認）で進み、成功時に `Migrated`
へ収束する。legacy binary は自動削除せず「削除可能」表示のみ。

```
# 前提: legacy install が存在する（/usr/local/bin/siderostat[-monitor]、
#       ~/Library/LaunchAgents/local.siderostat.{runtime,monitor}.plist）
# agent が事前確認
launchctl print "gui/$(id -u)/local.siderostat.runtime"   # legacy job 稼働確認
./scripts/e05-verify.sh snapshot pre-migration-legacy

# ユーザー（GUI）: first launch / migration フローで migration を実行
#   menu bar → migration 案内 → 承認

# agent が検証
./scripts/e05-verify.sh jobs         # new job running、legacy job 不在
./scripts/e05-verify.sh processes    # 重複 process がないこと
./scripts/e05-verify.sh ports        # port 重複（18080/18081/9920/18082/9911/8000）がないこと
ls ~/Library/Application\ Support/siderostat/migration-backup/   # legacy plist 退避
ls /usr/local/bin/siderostat*        # legacy binary は残存（削除しない）
./scripts/e05-verify.sh compare pre-migration-legacy post-migration-b11   # user data 不変
```

- 受入: old/new runtime が同時に同じ port を listen しない。DS4 child 重複なし。

#### シナリオ 2（失敗 migration → rollback）

new registration または readiness を意図的に失敗させ、legacy plist を backup から戻して
以前の job を再開する。cutover 状態機械は全 action の失敗で `RollingBack` へ遷移し、
rollback 成功で `RolledBack`、rollback 失敗で `RollbackFailed`（手動介入要求）となる。

```
# ユーザー（GUI）: migration 実行を意図的に失敗させる（registration/readiness を故障注入）
# agent が検証
./scripts/e05-verify.sh jobs         # legacy job が復旧していること
./scripts/e05-verify.sh ports        # port 重複なし
ls ~/Library/Application\ Support/siderostat/migration-backup/   # backup 状態
./scripts/e05-verify.sh snapshot post-rollback-legacy
./scripts/e05-verify.sh compare pre-migration-legacy post-rollback-legacy   # user data 不変
```

- 受入: rollback 後 legacy job が再開、port / child 重複なし。user data は不変。

#### シナリオ 3（candidate 間 upgrade）

package は単一 `/Applications/Siderostat.app` payload、`BundleIsRelocatable=false`。
upgrade はこの app を新しい署名済み bundle で更新し、user data / model / cache / secret は
保持する（仕様 13.1）。

現行は build 11 のため、upgrade は **build 10 → build 11** の方向で検証する。まず build 10 を
install してから build 11 で upgrade する。

```
# 0) 事前: 現行 build 11 を snapshot 採取し、明示的 rollback package で build 10 の検証起点を作る
./scripts/e05-verify.sh snapshot pre-s3-resume-b11
sudo installer -pkg /tmp/Siderostat-0.3.0-rollback.pkg -target /
#   （app は build 10、runtime は build 11 のまま。version mismatch 通知を確認可能）
./scripts/e05-verify.sh snapshot pre-upgrade-b10

# 1) upgrade: build 10 → build 11（agent、sudo）
sudo installer -pkg /tmp/Siderostat-0.3.0-build11-upgrade.pkg -target /

# 2) agent が事後 snapshot を再採取し、user data 不変を比較
./scripts/e05-verify.sh snapshot post-upgrade-b11
./scripts/e05-verify.sh compare pre-upgrade-b10 post-upgrade-b11   # config/secret/manifest が一致

# 3) ユーザー（GUI）: active runtime が旧 image で動き続ける場合、
#    menu bar → 「siderostat-runtimeを再起動」で明示的に再起動
# agent が再起動後の readiness / version を確認
./scripts/e05-verify.sh readiness
```

- 受入: config、secret、manifest、model、KV cache が保持（`compare` が PASS）。
  app/runtime version 不一致は monitor が通知し、ユーザーの明示操作で再起動できる。

#### シナリオ 4（prior package への rollback／シナリオ3起点で検証済み）

シナリオ4は、シナリオ3の build 10 → build 11 upgrade を成立させるための起点化プロセスで
実施済みである。独立した rollback の再実施は行わない。

- `Siderostat-0.3.0-rollback.pkg` を両ノードへ適用し、app build 10 / runtime build 11 を確認した。
- 両ノードで version mismatch 通知を確認した。
- `pre-upgrade-b10` の user data digest / secret mode を取得し、通常 build 11 upgrade 後の
  `post-upgrade-b11` と比較した結果は PASS だった。
- model、manifest、secret、KV cache は rollback / upgrade のいずれでも削除されなかった。

判定: version mismatch、prior package の適用、data 保持、通常版への復帰を確認済みであり、
シナリオ4の受入条件は PASS。シナリオ3の検証過程と重複するため、独立シナリオとして再実施しない。

> [!NOTE] シナリオ 3/4 の関係
> 現行が build 11 のため、rollback package で build 10 起点を作り、version mismatch を確認した後、
> 通常 package で build 11 へ戻す一連の流れをシナリオ3の実機検証として実施した。この過程が
> シナリオ4の受入条件も満たすため、シナリオ4を別 change window で繰り返さない。

### 4.3 実機検証の実行タイムライン・復元・user data 保護

実機検証を開始する前に、本節の手順で **user data のバックアップ**を取り、検証後の復元経路を
固定する。これは実機 gate を安全に閉じるための必須準備である。

#### 4.3.1 user data バックアップ（両機、検証前に実施）

```
# agent（sudo 不要）: user data を検証前の隔離 path へバックアップ
# 対象: config / secrets / manifests / cluster-state / KV cache / model（model・KV cache は
#       巨大なため、必要に応じて digest 記録のみで代替可）
BACKUP_ROOT=/tmp/siderostat-e05-backup-<ts>
mkdir -p "$BACKUP_ROOT"
cp -R ~/Library/Application\ Support/siderostat "$BACKUP_ROOT/appsupport"
# secrets の mode（0600）を保持
# 巨大な model / KV cache は削除対象にしないため digest 記録のみで可
shasum -a 256 ~/Library/Application\ Support/siderostat/config.toml \
    > "$BACKUP_ROOT/config.sha256"
./scripts/e05-verify.sh snapshot pre-verify-backup
```

- バックアップは検証中に user data が万一変化した場合の復元経路。
- 受入基準「data loss がない」の比較元としても使用。
