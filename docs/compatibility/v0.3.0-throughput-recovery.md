## Opt-in automatic recovery

change window 内だけ両 node の config に `[recovery] enabled = true` を追加し、
検証終了後に元の config へ復元した。故障注入は coordinator の管理対象
`ds4-server` child 一件に限定し、in-flight request 中に一時停止して
first-token timeout を作成した後、`SIGCONT` で通常の recovery stop 処理へ戻した。

## Cooldown and final restore

同じ first-token stall を二回目だけ作成したところ、次の metrics になった。

```text
ds4_proxy_recovery_events_total{event="started",reason="first-token-timeout"} 1
ds4_proxy_recovery_events_total{event="completed",reason="first-token-timeout"} 1
ds4_proxy_recovery_events_total{event="suppressed",reason="cooldown"} 1
```

二回目の recovery job は作成されず、cluster state は DistributedReady のまま維持
された。故障注入 child は再開し、in-flight は `0` へ戻った。

最後に両 node の config を検証前のバックアップへ戻し、runtime を通常再起動した。
最終確認は次のとおりである。

- config に `[recovery]` はなく、automatic recovery は既定の `enabled=false`。
- 両 node の `cluster doctor --json` は `healthy=true`。
- 両 node の admission は `serving`、in-flight は `0`。
- 両 node の final canary は HTTP 200 / `healthy`。
- 管理対象の distributed `ds4-server` child は各 node 1件で、orphan はない。

Final canary は MacBook Pro が TTFB 941 ms / 1 token、Mac Studio が TTFB 3248 ms /
1 token であった。chunk TPS は短い1-token応答のため性能比較用の値には使用しない。

## Operational handoff

Hermes の cron 実行前には、同じ endpoint に対して doctor と bounded canary を一回
実行する。canary が `healthy` でない場合は cron を開始せず、既存 recovery status と
operator action を確認する。Hermes の暫定 stale deadline は 1800 秒、Siderostat の
`first_body_byte` / `stream_idle` は 2400 秒とし、canary はこれらの timeout の代替では
なく、cron 開始前の軽量な serving gate として扱う。

## Known installation caveat

MacBook Pro では、build15 の ad-hoc bundle 置換後に旧署名由来の Service Management
登録が stale となり、通常の `SMAppService` unregister が code 57 で失敗した。
Mac Studio は再登録後に正常起動した。H-10 recovery 自体は MacBook Pro の product-owned
runtime を同一ユーザーの launchd job として一時復帰させて実施した。この workaround は
recovery evidence のためのもので、通常配布の fresh install / app update acceptance
とは分離する。bundle 更新時の unregister → register を起動処理へ組み込むことを、別の
macOS lifecycle follow-up とする。
