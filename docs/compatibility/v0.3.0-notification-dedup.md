## 9. 再収束反復の原因再調査

前節の時系列を source と照合した結果、前回の lifecycle owner 修正だけでは原因を取り切れていない
ことを確認した。直接の因果は次の通りである。

1. `/admin/restart` は `ProductionClusterRuntime::stop_distributed()` を呼ぶが、これは coordinator／
   worker のローカル distributed child を停止するだけで、peer へ計画停止を通知しない。
2. restart signal が server loop に届いて reconcile task が abort されるまで、現在の process の
   reconcile／route-loss monitor は動作可能なままである。
3. coordinator の control endpoint が停止すると peer の lease が失効する。peer 側の通常の
   `reconcile_peer` は `DistributedReady` を `PeerLost` として `recover_from_peer_loss` に渡し、
   Solo Standalone へ fallback する。
4. coordinator 側では `auto_pair=true`、`auto_promote=true` の reconcile task が Solo/Paired から
   自動復帰を試みる。再起動中の control session／worker hello が安定する前にこの処理が走るため、
   Solo/Paired／worker hello 待ちが反復する。

既存の `automatic_pairing_blocked` は deployment mismatch 用であり、計画 restart 中の peer-loss
recovery を抑止する状態ではない。また、既存の coordinator 側 `begin_drain`／`stop_worker` の制御
経路は通常の demotion/promotion failure 用で、graceful process restart からは呼ばれていない。
したがって次の修正対象は child の停止方法ではなく、計画 restart の cluster-wide admission／
reconcile suppression／peer acknowledgement を持つ restart protocol である。

## 10. 計画再起動プロトコル実装

2026-08-25、上記原因に対して次の実装修正を行った。

- authenticated control plane に `prepare-restart` / `cancel-restart` command を追加した。
- coordinator は distributed graceful restart の開始時に local gate を立て、worker の
  `prepare-restart` ACK を受けてから既存の demotion lifecycle を実行する。
- planned-restart gate 中は reconcile、PeerLost recovery、route-loss demotion、automatic
  Pair/Promote を開始しない。
- worker は再起動後に新しい `Pair` を受信した時点で gate を解除する。
- drain timeout、peer preparation failure、child stop failure では gate を解除して再試行可能にする。

control protocol、worker/coordinator phase、graceful restart の既存 test を含む全 `cargo test
--all-targets`（265 tests）、`cargo clippy --all-targets -- -D warnings`、format、diff-check は
PASS である。これはコード検証の evidence であり、実機 artifact の N-03 受入 evidence ではない。
実機では次の修正版 build を両 node に適用し、`DistributedReady → PairedStandaloneReady →
DistributedReady` の単一復帰経路、Solo 遷移なし、通知履歴、metrics/structured log を確認する。

## 17. build26 の追加競合修正と配置

build25 の実機適用前に、早期 `Demote` ACK と新 coordinator の再接続が重なる場合を追加監査した。
worker は `Demote` の制御応答を先に返すため、応答後も旧 distributed child の停止処理が継続する。
この間に新 coordinator の `Pair` が到着すると、従来の build25 修正では Pair effect が planned
restart gate を解除し、worker の実状態がまだ `DistributedReady`／child 停止中でも
`PrepareWorker` を受け付ける競合が残っていた。これにより制御 phase だけが `WorkerPreparing` に
進み、worker の実状態検査で失敗した後に再収束できなくなる可能性がある。

追加修正では planned restart を単一の atomic gate で管理し、次を保証する。

- child 停止中に到着した Pair は保留し、停止完了後にだけ reciprocal Pair、安定待ち、reconcile を実行する。
- child 停止中の `PrepareWorker` は `409 worker planned restart is still in progress` で拒否し、control phase を変更しない。
- Pair の同時実行や停止完了処理の二重実行を gate の compare-and-exchange で抑止する。
- coordinator が再起動途中で reciprocal Pair に失敗した場合は、child 停止済み状態を保持して後続 Pair で再試行できる。

全 `cargo test --all-targets`（271 tests）、`cargo clippy --all-targets -- -D warnings`、format、diff-check は
PASS。修正を含む内部検証用 build26 DMG は `dist/native-build26/Siderostat-0.3.0.dmg`、SHA-256 は
`a1749436c1aaf4cb7296e38c95ed1f9844fb2d0c9ddb87ec7b2ab11d4aa590f1`。同一ファイルを MacBook Pro と
Mac Studio の `/tmp/Siderostat-0.3.0-build26.dmg` に配置し、両 node の checksum 一致を確認した。
build26 は secure timestamp／notarization を含まない ad-hoc 内部検証 artifact であり、実機での
coordinator-only restart 再検証が完了するまで N-03 の受入 evidence には採用しない。

## 18. build26 coordinator-only restart の実機結果

2026-08-26、build26 を両 node へインストールし、両 node が `DistributedReady` であることを確認した後、
ユーザーが Mac Studio の Monitor から `siderostat-runtimeを再起動` を一回実行した。再起動直後は
Mac Studio が一時的に standalone、MacBook Pro が ready 待ちとなったが、再接続・worker hello・分散 child
起動が完了した後、両 node は安定して次の状態になった。

- MacBook Pro: `healthz` build26、`readyz 200`、`admission=serving`、`in_flight=0`、
  `distributed-worker` generation 761 / PID 10139 running
- Mac Studio: `healthz` build26、`readyz 200`、`admission=serving`、`in_flight=0`、
  `distributed-coordinator` generation 1407 / PID 59194 running
- 両 node: `state=distributed-ready`、`mode=distributed-layer-parallel`、peer lease は
  `present=true`／`route-scoped=true`／`valid=true`、standalone child は停止済み
- runtime LaunchAgent は両 node とも `running`。Mac Studio は restart 後の `runs=2`、新 runtime PID
  59052 を確認した。期待される distributed child 以外の orphan は `/cluster` 上に存在しない。

Mac Studio の遷移は `solo-standalone-ready → paired-standalone-ready → awaiting-worker-hello →
promoting → distributed-starting → distributed-ready` の一連で完了した。build24 まで観測した
`demoting`／`unavailable-transition` 固着、runtime 世代不変、child 不在は今回再現せず、再起動後の
追加収束待ち 20 秒を含めても `DistributedReady`／`Serving`／`in_flight=0` を維持した。coordinator の
`target=local-standalone` は distributed coordinator の内部 target 解決仕様であり、`readyz 200` と
矛盾しない。

以上により、build26 の短い停止経路に関する技術 gate（再起動、再収束、serving safety、child／orphan、
generation）は PASS とする。

通知履歴レビュー（ユーザー確認、2026-08-26）では、Mac Studio に開始前の baseline として
`DistributedReady` が1回あり、coordinator restart の recovery epoch 内には次の4件が各1回だけ記録された。

- `5秒後に再起動`: 1回
- `Standalone 起動`: 1回
- `Paired / ノード検出`: 1回
- `最終 DistributedReady`: 1回

開始前の `DistributedReady` は再起動 epoch 外の既存状態通知であり、重複通知とは数えない。recovery epoch
内の Solo／Paired 相当通知は各1回、最終 `DistributedReady` も1回で、重大通知の欠落・反復はなかった。
したがって、build26 の短い停止経路と通知回数の実機受入を PASS とし、N-03 を完了とする。
